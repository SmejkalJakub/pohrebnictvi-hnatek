# Editable fields policy

**Status:** Phase 1 contract, draft 1 (2026-11-05); CMS sections updated for Decap CMS 2026-11-12.

This document says who may change what, and through which interface. It is the source for the generated Decap CMS configuration (`public/admin/config.yml`, generated by `tools/cms/decap-config.ts`; see [cms/architecture.md](cms/architecture.md)).

Related: [content-contract.md](content-contract.md) · [template-contract.md](template-contract.md)

---

## 1. Actors and interfaces

| Actor | When | Interface | Scope |
| --- | --- | --- | --- |
| **Template developer** | template build and maintenance | system repo source | everything in `core/` and `templates/` |
| **Production agent** (AI session, supervised by an operator) | before handover | client content files, `site.config.ts`, `provenance/` | content and declared template options; **never facts without provenance** |
| **Operator** (human running the pipeline) | before handover | same as the agent, plus sign-off records | records client approvals; sets ledger `VERIFIED` |
| **Client editor** (non-technical) | after handover (and in the pilot) | Decap CMS at `/admin/` (login through DecapBridge, no GitHub account) | the CMS-editable fields in §4 only |
| **Repository owner** (client or their developer) | after handover | Git source | everything. This is outside the CMS contract and is stated in HANDOVER.md. |

**Design and layout are never CMS-editable.** Templates, CSS, tokens, typography, layout, page structure, routes, navigation structure, code, dependencies and deployment config are all outside the CMS, with no exceptions.

## 2. Policy levels

| Level | Meaning |
| --- | --- |
| **CMS** | Visible and editable in Decap CMS, with the widget and validation listed. |
| **CMS (toggle)** | Editable only as a boolean or select from fixed options. |
| **Agent** | Set by the agent/operator before handover; not shown in the CMS. Changeable later only through source. |
| **Locked** | Set by the template or core; never changed per client except through a template release. |
| **Hidden** | Declared in `config.yml` as a `hidden` widget: kept as it is on save, never displayed (e.g., `placeholder`, `id`). Every key the content holds is declared, including keys inside list items; `tools/cms/tests/decap-config.test.ts` checks this against the real client content. |

## 3. Production agent rules (before handover)

The agent **may**:

- populate content fields from ledger facts, copying values exactly. A value that is not in the ledger is not written.
- draft Czech copy (page bodies, service descriptions, guidance) based on ledger facts. Each drafted file is recorded as `DRAFT` in `approvals.json`.
- create placeholder entries (`placeholder: true`), neutral placeholder images (`source: "placeholder"`) and demo prices (`status: "demo"`) for prototype review.
- choose template options and homepage section order within the manifest's declared values.
- set feature flags: `articles` stays `false` for Hnátek. `contactForm` is on for both Hnátek variants **for testing on Netlify only** (`contactFormHandler: "netlify"`); production stays blocked until U9 is resolved (privacy page text covering the form, recipient). The form's wording is template copy, not a CMS field.
- set `pricing.visible` to `false` if no prices are approved.

The agent **must not**:

- invent or "complete" a fact: names, dates, years, IČO, addresses, coordinates, prices, testimonials, quotations, service offerings, service area.
- set ledger status `VERIFIED`, or record any approval. Only the operator can, and only on the client's explicit confirmation, recorded with name, date and method.
- set `PriceItem.status = "approved"` or `ImageRef.rightsConfirmed = true` without recorded evidence in `approvals.json`.
- set `ImageRef.depicts = "actual-business"` for anything not supplied by the client or copied from the client's own site with permission.
- generate imagery that depicts, or could be read as, the real premises, staff, family members or the Cadillac.
- edit template source, tokens or CSS for a single client (template-contract §8).
- turn `SITE_MODE` to `production` on any deployment before `npm run check:launch` passes.

## 5. CMS validation and failure handling

- **The CMS is a convenience; the build is the gate.** Decap field constraints (`required`, `pattern`, selects) give early feedback. Zod and the publication gate are authoritative, and they run on every preview and publish build. Optional numbers carry no `min`/`max` in the CMS (Decap rejects an empty optional number that has them); the schema enforces the range.
- **No silent publication of invalid data:** a commit that fails validation produces a failed build, so nothing deploys and the previous version stays live. The host must be configured to e-mail the client and operator on failed deploys (Phase 6). The gate prints Czech messages with the file and field.
- **Where errors appear:** Decap marks invalid fields in the form and refuses to save. Cross-field rules (time order, price `kind`/`amount`, duplicate ids) exist only at build time; their Czech messages appear in the preview and publish runs on GitHub (Actions log).
- **Branches and publishing** ([cms/publishing.md](cms/publishing.md)): the editor saves to branch `content`, which `preview.yml` builds as the noindex preview. Production changes only through `publish.yml`, started by the agency: integrity check (only content may differ from the export), production build with the gate, deploy, then a fast-forward of `main`. Decap's editorial workflow (branches and pull requests per entry) is not used.
- **Recovery:** Decap has no revert. A broken edit is fixed forward in the CMS, discarded with `discard.yml` (resets `content` to `main`) before publishing, or reverted in GitHub; a published deploy can also be rolled back at Cloudflare.
- **Dates:** every date field declares `default: ""`, so the editor never pre-fills today's date (tested in Decap 3.17.3: an empty `review.reviewedAt` stays `null` after a save).
- **Image rights follow the file.** Decap keeps an image's other keys when the photo is replaced, so the admin page records the file a rights confirmation belongs to (`rightsConfirmedFor`) and clears the confirmation when the file changes; G-033 rejects a confirmation recorded for another file.
- **Generated, not hand-written:** `config.yml` is generated by `tools/cms` from this policy, the template manifest (`pageFields`, `imageSlots`, `supports`), the features and the client's `publishing.json`. A collection is generated only when its feature is on **and** the template supports it, so Hnátek has no articles, notices, people, FAQ or documents editor. PDF fields (notices, documents) upload into `src/assets/documents`.
